# Phase 4.2: The Chaos Suite on k3d Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Eight chaos scenarios (crash, rolling restart, cut from Kafka), each run during one checked replay on k3d, with the checker's verdict as the scenario's verdict; plus the product fixes they need (#9, #10, #17, #31, #44), the checker's fixes (#48, #49), and two copies of Stage 1, Stage 2, and the gateway by default.

**Architecture:** `scripts/chaos-lib.sh` holds the fault primitives (crash through `crictl` on the k3d node, cut as a NetworkPolicy plus `conntrack -D`, group membership, steadiness); `scripts/chaos.sh` runs a scenario: start a checker Job, wait for its "run started" line, inject at 40% of the replay, prove the fault landed, collect the verdict. Stage 2's delivery script records each delivery's Redis `TIME` in its claim, and the checker excuses a missing socket push only if the socket was down within 2 s of it.

**Tech Stack:** Java 17, Jedis 4.4.7, kafka-clients 4.3.1, JUnit 5, Testcontainers, bash, kubectl, Helm, k3d (Kubernetes v1.35.5), Strimzi 1.2.0, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-11-phase-4-2-chaos-design.md`

## Global Constraints

- Scenarios, in this order: `stage1-crash`, `stage2-crash`, `history-crash`, `gateway-crash`, `gateway-rollout`, `broker-crash`, `stage1-cut`, `stage2-cut`.
- Each scenario: one checker run, `SET=evening`, `SPEED=60` by default; fault at 40% of the replay, timed from the `[Checker] run started` line.
- Crash: `docker exec k3d-<cluster>-server-0 crictl stop --timeout 0 <containerId>`; proof: restart count up and `lastState.terminated.exitCode` = 137.
- Cut: label `chaos=cut`, NetworkPolicy `chaos-cut` (Egress; allow Redis 6379 to pods `app.kubernetes.io/name: redis`, DNS 53 UDP+TCP to any namespace), then `conntrack -D -s <podIP> -p tcp --dport 9092` on the node; held 60 s; membership checked at 50 s; heal = delete policy, remove label.
- Target pod: the first pod in name order of its Deployment; broker pod `<release>-dual-role-0`.
- Steady before each scenario: up to 180 s for every Deployment ready and groups `stage1`, `stage2`, `history` having as many members as pods.
- Excuse window for a missing socket push: delivery time ± 2000 ms, in Redis time.
- Claim value: delivery time in ms, `seconds × 1000 + floor(microseconds / 1000)` from the script's `TIME`; dedup stays `EXISTS`.
- Deadlines: check = replay minutes × 60 ÷ `SPEED` + 900 s; replay = … + 300 s; `check-clean` 600 s; chart defaults `checker.activeDeadlineSeconds: 3600`, `replay.activeDeadlineSeconds: 14400`. Replay minutes: `ci` 136, `evening` 192.
- Gateway: `lifecycle.preStop.sleep.seconds: 5`; `terminationGracePeriodSeconds` stays 30.
- Replicas 2: `stage1-worker`, `stage2-worker`, `gateway`. History stays 1.
- Output: `target/chaos/<UTC yyyymmddThhmmZ>/<scenario>.log` and `summary.txt`.
- Redis keys only via `util/RedisKeys.java`; every Jedis handle in try-with-resources; config by env var with defaults; comment density as in the repo (explain *why* at the claim time, the excuse rule, the cut's conntrack step, the shutdown order).
- `make test` green at the end of every Java task.

## Review Focus

1. **A claim that holds `'1'`** (written before the deploy) or anything not a number → Stage 2 still dedups; the checker reads it as "no delivery time" and reports a finding, never throws (Task 2 `legacyClaimStillDedups`, Task 3 `nonNumericClaimIsNoDeliveryTime`).
2. **A socket still down when the run ends** (open gap, `toMillis = Long.MAX_VALUE`) with a negative clock offset → no overflow; a push delivered inside the gap is excused (Task 3 `openGapAtEndExcusesWithoutOverflow`).
3. **Ctrl-C or a script error during a cut** → the cluster is healed anyway: no `chaos-cut` policy, no `chaos=cut` label left (Task 10 step "interrupt mid-cut").
4. **Back-to-back scenarios** while the last one's restarted pod is still rejoining → the next scenario waits for steady instead of starting on a half-formed group (Task 10 runs two scenarios in a row and checks the steady line in the log).
5. **`make check SET=<a set with no replay length>`** → make stops with `unknown replay set <name>` before creating a Job, instead of a Job with a nonsense deadline (Task 4 step).
